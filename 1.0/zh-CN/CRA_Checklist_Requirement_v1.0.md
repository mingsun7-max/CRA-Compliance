# **第 1 节：引言与范围**

CRA 是否适用，并非仅取决于组织是否在欧盟部署开源软件。首要的范围判断问题是：组织是否在欧盟市场提供含数字要素的产品，或者是否以其他方式承担 CRA 所涵盖的角色，例如制造商、进口商、分销商、授权代表或开源软件管理者。

如果组织既不在欧盟市场提供含数字要素的产品，也不承担 CRA 所涵盖的角色，则本清单所涉及的要求可能不适用于该组织。此类组织仍可自愿将本清单作为了解 SBOM、漏洞处理、证据管理及软件供应链准备工作的参考。

《OpenChain CRA 合规要求与检查清单》是一项由社区维护、与 OpenChain 保持一致的自我认证与准备度参考资源，供组织为履行欧盟《网络韧性法案》（CRA）义务作准备。本清单映射至欧盟第 2024/2847 号条例，并与 ISO/IEC 18974、ISO/IEC 5230 及包括 BSI TR-03183 在内的相关 SBOM 指引衔接。其涵盖治理、产品评估、SBOM 质量、漏洞处理、监管报告、开源软件管理、技术文档证据、安全更新及供应链义务。

CRA（欧盟第 2024/2847 号条例）对投放欧盟市场的含数字要素的产品（PDE）规定了强制性网络安全要求。以下角色定义取自 CRA 第 3 条：

**角色定义（CRA 第 3 条）：**

● 制造商（第 3 条第 (13) 项）：开发或制造 PDE，或委托他人设计或制造 PDE，并以其自身名称或商标销售该产品的自然人或法人，无论该产品是有偿、免费，还是作为产生货币收入的服务提供。

● 进口商（第 3 条第 (16) 项）：在欧盟设立，将带有欧盟境外自然人或法人名称或商标的 PDE 投放市场的自然人或法人。

● 分销商（第 3 条第 (17) 项）：供应链中除制造商或进口商以外，在欧盟市场提供 PDE 的自然人或法人。

● 开源软件管理者（OSS Steward；第 3 条第 (14) 项）：制造商以外，持续为符合自由和开源软件（FOSS）条件的产品开发提供支持，并确保这些产品可持续存续的法人。开源软件管理者的定义、范围和义务规定于 CRA 第 3 条第 (14) 项、序言第 18、19 段及第 24 条。

**本文件的范围：**

● 由 [填写：制造商法定全称] 投放欧盟市场的所有含数字要素的软件产品

● 已发布产品中包含的开源组件

● 软件供应链流程，包括 SBOM 生成、漏洞管理和披露

● 参与开发、安全运营、法律及合规工作的人员与流程

硬件范围说明：硬件专属要求（包括 §3.1.7 硬件物料清单）仅适用于包含实体硬件组件的产品。仅提供软件的组织可以将硬件专属检查项标为“不适用（N/A）”，并记录理由。

# **第 3 节：组件管理与 SBOM 质量**

本节规范 SBOM 的质量与完整性。CRA 第 13 条要求制造商以足以识别已知漏洞的细粒度记录组件。OpenChain ISO/IEC 18974 要求建立形成文件的组件识别与漏洞跟踪流程。

<a id="31-software-identification--bill-of-materials"></a>
## **3.1 软件识别与物料清单**

为所有已发布产品生成机器可读 SBOM 的流程。CRA 要求 SBOM 至少覆盖这些产品的顶层依赖项。

| 编号 | 要求 | 是否符合？（是／否／部分符合） | 证据与理由 | 指引／参考 |
| :---- | :---- | :---- | :---- | :---- |
| **3.1.1** | [CRA 要求] 组织必须维持形成文件的流程，为所有已发布产品生成机器可读的 SBOM，至少覆盖这些产品的顶层依赖项。 | ☐ 是 ☐ 否 ☐ 部分符合 | | SBOM 生成程序；工具配置（如 Syft、Trivy、CycloneDX CLI）。参考：BSI TR-03183。 |
| **3.1.2** | [CRA 要求] SBOM 必须采用常用的机器可读格式，如目前受支持版本的 SPDX 或 CycloneDX，并必须符合任何适用的实施法案、协调标准或共同规范。 | ☐ 是 ☐ 否 ☐ 部分符合 | | SBOM 文件样本；格式校验报告。SBOM 内容要求参见 BSI TR-03183-2。 |
| **3.1.3** | [良好实践] SBOM 生成宜集成到软件交付流水线，并在每次发布构建时生成制品。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 软件交付流水线配置摘录；构建制品清单。 |
| **3.1.4** | [CRA 要求] SBOM 必须以常用的机器可读格式至少覆盖产品的顶层依赖项。[良好实践] 在技术可行或为识别、评估和修复影响产品的漏洞所必需的情况下，SBOM 还可以包含传递依赖及嵌入式依赖。宜记录任何未覆盖的组件或依赖层级，并记录基于风险的理由，以及为确保有效漏洞管理而采用的替代措施。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 工具深度配置；附有基于风险理由的排除项记录；SBOM 样本组件数量与依赖图的对比审计。 |
| **3.1.5** | ⚠ 截止日期：2026 年 9 月 11 日——⚠ [良好实践] 组织宜记录目标 SBOM 深度的决定，并说明与下述能力相关的运营理由：能在 24 小时内确定某个正被主动利用的 CVE 是否影响任何已交付产品。深度决定宜承认实施限制，明确每种产品或构建类型的预期依赖深度，并解释如何监测尚未解析的传递依赖或管理其风险。仅覆盖顶层的 SBOM 对涉及传递依赖的场景可能不足。 | ☐ 是 ☐ 否 ☐ 部分符合 | | SBOM 深度政策；将深度与 24 小时时限关联的运营理由；自动将 CVE 与 SBOM 匹配的测试证据；针对尚未解析依赖层级的监测方法文件。 |
| **3.1.6** | [CRA 直接义务] SBOM 必须采用常用的机器可读格式编制，并必须至少覆盖产品的顶层依赖项。[组织 SBOM 配置要求／实施控制] 组织的 SBOM 配置要求宜包括产品级元数据（产品名称、版本、供应商、发布日期、唯一产品标识符），以及每一组件的组件级元数据（组件名称、版本、供应商、PURL、CPE 或 SWHID（ISO/IEC 18670）等唯一组件标识符、密码学哈希值，以及包括声明许可证和判定许可证在内的许可证信息）。这些附加字段支持实施、可追溯性、与 CISA 最低要素及 ISO/IEC 18974 的衔接，以及 ISO/IEC 5230 合规证据，但并非被表述为 CRA 的法定最低要求。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 将 SBOM 字段映射至 CRA 附件 I（首要要求）、CISA《2025 年 SBOM 最低要素》（作为替代 2021 年 NTIA 最低要素的资料性参考），以及 BSI TR-03183-2（德国市场的实施指引）。这些参考资料存在差异时，以 CRA 附件 I 为优先。SWHID 参考：https://swhid.org。参考：[BSI TR-03183](https://www.bsi.bund.de/EN/Themen/Unternehmen-und-Organisationen/Standards-und-Zertifizierung/Technische-Richtlinien/TR-nach-Thema-sortiert/tr03183/TR-03183_node.html)。 |
| **3.1.7** | [良好实践] 对包含实体硬件组件的产品，宜在 SBOM 之外维护硬件物料清单（HBOM），以识别硬件组件及其固件依赖。对于机器可读的 HBOM 交换，推荐采用 CycloneDX（ECMA-424／CycloneDX 1.7 或更高版本）；在生成方和使用方工具均支持时，可以使用 SPDX 3.x 硬件配置文件。仅提供软件的组织可以将本项标为不适用，并记录理由。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 机器可读的 HBOM（优先 CycloneDX／ECMA-424；支持时使用 SPDX 3.x 硬件配置文件）；硬件组件清单；固件版本登记册。 |
| **3.1.8** | [良好实践] 组织宜维护具有锁定版本及已批准组件条目的依赖项登记库，以确保不同构建之间的 SBOM 可复现。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 依赖锁定文件；软件包登记库配置；已批准组件清单。 |

<a id="32-data-quality--completeness"></a>
## **3.2 数据质量与完整程度**

校验 SBOM 完整程度、组件粒度以及处理“已知的未知项”的标准。

| 编号 | 要求 | 是否符合？（是／否／部分符合） | 证据与理由 | 指引／参考 |
| :---- | :---- | :---- | :---- | :---- |
| **3.2.1** | [良好实践] 发布前宜通过自动或人工审查，对 SBOM 应用完整程度校验关卡。 | ☐ 是 ☐ 否 ☐ 部分符合 | | SBOM 检查工具输出（如 sbom-scorecard、ort）；CI 关卡通过／失败日志。 |
| **3.2.2** | [符合性证据／实施控制] 组织宜维持明确政策，处理“已知的未知项”——即无法完全确定其身份的组件——并将其与有意不披露的专有代码区分。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 针对未知组件的政策文本或 SBOM 注释约定。 |
| **3.2.3** | [符合性证据／实施控制] 宜对 CRA 附件 I 要求的 SBOM 最低必需字段进行校验；在 SBOM 签署确认前，可以将 BSI TR-03183-2 字段校验作为实施参考。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 校验规则集；被拒绝的 SBOM 及其整改示例。 |
| **3.2.4** | [良好实践] 宜跟踪并定期审查 SBOM 质量指标（如完整程度评分、字段填充率）。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 仪表板截图或指标报告。 |
| **3.2.5** | [良好实践] 能识别完整软件包时，宜避免使用文件级或代码片段级 SBOM 引用。如果使用文件级或代码片段级引用，SBOM 宜明确标示粒度，尽可能将引用映射至最小的完整软件包，并在无法进一步跟踪依赖时说明依赖链是否在该处终止。 | ☐ 是 ☐ 否 ☐ 部分符合 | | SBOM 样本；软件包映射理由；代码片段／文件级例外记录；依赖链终止说明。 |

<a id="33-provenance--integrity"></a>
## **3.3 来源与完整性**

用于核验软件来源、防止篡改、跟踪变更及保障构建基础设施安全的机制。

| 编号 | 要求 | 是否符合？（是／否／部分符合） | 证据与理由 | 指引／参考 |
| :---- | :---- | :---- | :---- | :---- |
| **3.3.1** | [符合性证据／实施控制] 为支持 CRA 符合性证据及供应链完整性而有需要时，已发布产品中的组件宜具有经核验的来源信息，如上游仓库网址、提交哈希值、SWHID（ISO/IEC 18670）或经核验的软件包登记库坐标。 | ☐ 是 ☐ 否 ☐ 部分符合 | | SBOM 的 externalRef 字段；PURL 条目；SWHID 标识符；可复现构建制品。 |
| **3.3.2** | [符合性证据／实施控制] 为支持完整性证据及发布可追溯性而有需要时，宜记录发布制品的密码学校验和，如 SHA-256 或更强算法的校验和。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 含哈希值的制品清单；签名密钥文档。 |
| **3.3.3** | [良好实践] 宜通过变更跟踪机制记录各发布版本间组件的新增、移除及版本更新。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 相邻发布版本间的 SBOM 差异报告；变更日志集成。 |
| **3.3.4** | [良好实践] 宜对发布制品进行软件签名或出具证明（如 Sigstore、in-toto、SLSA 来源证明）。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 签名工作流；供客户使用的核验命令。SLSA 框架：[slsa.dev](https://slsa.dev)。 |
| **3.3.5** | [良好实践] 组织宜维持形成文件的安全构建基础设施政策，覆盖构建环境隔离、可复现性及完整性核验。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 构建环境配置；可复现构建证据；基础设施即代码仓库。 |
| **3.3.6** | [良好实践] 构建流水线宜与开发环境隔离，且必须将生产构建系统的访问权限限制为仅授权人员可访问。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 构建系统访问控制政策；构建系统访问审计日志。 |
| **3.3.7** | [良好实践] 构建制品宜在干净、可复现的环境中生成，并在提升为正式发布制品前进行核验。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 构建核验程序；洁净环境构建证据。 |
| **3.3.8** | [良好实践] 不得将秘密信息（API 密钥、签名密钥、凭据）嵌入源代码或构建制品。宜使用秘密信息管理方案。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 秘密信息扫描工具配置；秘密信息管理政策；显示不存在嵌入式秘密信息的工具输出。 |
| **3.3.9** | [良好实践] 用于发布制品证明的签名密钥宜存储于硬件安全模块（HSM）或同等密钥管理系统中。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 密钥管理政策；HSM 或 KMS 配置证据。 |
| **3.3.10** | [良好实践] 组织宜记录从源代码提交到发布制品的完整保管链，以便开展事件发生后的来源分析。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 构建来源证明（如 SLSA 来源证明）；制品沿袭关系文档。 |

| **3.3.12** | [良好实践] 宜通过流水线审计或自动完整性检查，定期核验构建流水线本身的完整性。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 流水线审计记录；完整性检查配置；异常检测证据。 |

<a id="34-secure-development-properties--security-testing"></a>
## **3.4 安全开发属性与安全测试**

本小节涵盖在产品设计中落实的网络安全属性及核验这些属性的测试，而不仅是发布测试。组织宜将安全架构设计、安全功能开发、威胁建模及核验实践纳入产品生命周期，使附件 I 要求的属性自始即被纳入设计。本节检查项为技术文档（§7.1）提供内容。

| 编号 | 要求 | 是否符合？（是／否／部分符合） | 证据与理由 | 指引／参考 |
| :---- | :---- | :---- | :---- | :---- |
| **3.4.1** | [CRA 要求] 产品必须在不含默认凭据的情况下交付。需要身份验证时，必须在首次使用时提示用户设置唯一凭据，并必须对网络暴露应用默认拒绝策略（CRA 附件 I 第 I 部分）。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 安全配置政策；产品启动流程文档；凭据政策测试记录。 |
| **3.4.2** | [CRA 要求] 必须实施攻击面最小化：必须默认禁用不必要的端口、服务及接口，并在入站连接登记册中记录。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 默认安全配置清单；入站连接登记册；网络暴露图；安全加固指南。 |
| **3.4.3** | [符合性证据／实施控制] 传输中的数据必须使用现行标准加密（TLS 1.2 或更高版本或同等标准）。网络安全风险评估识别出敏感性时，静态存储数据必须加密。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 加密政策；TLS 配置审计；数据分类图。 |
| **3.4.4** | [符合性证据／实施控制] 技术可行时，必须应用内存安全机制（如内存安全语言，ASLR、栈金丝雀、CFI 等编译器缓解措施）。任何例外必须连同补偿性控制措施形成文件。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 构建选项配置；语言或运行时选择理由；例外登记册。 |
| **3.4.5** | [符合性证据／实施控制] 静态应用安全测试（SAST）必须集成至 CI/CD 流水线，并针对每个候选发布版本执行。发布前必须解决严重及高危发现项，或正式接受相应风险。 | ☐ 是 ☐ 否 ☐ 部分符合 | | SAST 工具配置；扫描结果摘要；发现项处置记录。 |
| **3.4.6** | [符合性证据／实施控制] 至少每次重大版本发布都必须开展动态应用安全测试（DAST）或模糊测试，并必须记录结果。 | ☐ 是 ☐ 否 ☐ 部分符合 | | DAST 或模糊测试工具输出；结果分诊记录；修复证据。 |
| **3.4.7** | [符合性证据／实施控制] 至少每年或在发生重大架构变更时，必须开展渗透测试或基于威胁模型的结构化安全审查。宜定期采用独立评估。必须跟踪发现项直至修复。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 渗透测试报告或安全审查记录；发现项跟踪记录；修复签署确认。 |
| **3.4.8** | [符合性证据／实施控制] 安全测试证据（SAST 结果、渗透测试报告、DAST 输出）必须作为技术文档的一部分保留。保留期限：产品投放市场后至少 10 年；支持期更长的，按支持期保留（CRA 第 13 条第 13 款）。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 技术文档中安全测试制品的索引条目；保留政策。 |
| **3.4.9** | [符合性证据／实施控制] 必须为每项产品建立威胁模型，涵盖攻击面、威胁行为者、攻击向量及缓解控制措施。发生重大架构变更时，必须更新威胁模型。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 威胁模型文档；所用方法（如 STRIDE、PASTA）；更新历史。 |
| **3.4.10** | [符合性证据／实施控制] 必须设立形成文件的发布安全关卡，任何产品版本投放欧盟市场前都必须通过。该关卡必须核验所有严重及高危安全发现项均已解决或已正式接受风险。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 发布关卡清单；签署确认证据；已接受风险的例外日志。 |
| **3.4.11** | [良好实践] 组织宜维持形成文件的安全编码标准，涵盖输入验证、身份验证、会话管理、错误处理及密码技术使用，并必须就该标准的应用培训开发人员。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 安全编码标准文件；开发人员培训记录。 |
| **3.4.12** | [CRA 要求] 产品在市场提供时，必须不存在已知可利用漏洞。该要求是否适用于产品及其适用方式，由 §2.6 下的网络安全风险评估确定。 | ☐ 是 ☐ 否 ☐ 部分符合 | | 发布时附可利用性评估的漏洞登记册；未解决发现项的处置记录；发布批准。相关实施控制：§3.4.5-§3.4.7、§3.4.10。 |

<a id="section-4-vulnerability-handling--vulnerability-exchange-vex--csaf"></a>
# **第 4 节：漏洞处理与漏洞信息交换（VEX／CSAF）**

CRA 第 13 条第 6 款要求制造商无不当延迟地处理漏洞。第 14 条规定了向 CRA 单一报告平台（SRP）进行强制性三阶段报告的流程。本节界定从信息接收到披露及监管通知的端到端漏洞生命周期。

<a id="41-vulnerability-ingestion--monitoring"></a>
## **4.1 漏洞信息接收与监测**
